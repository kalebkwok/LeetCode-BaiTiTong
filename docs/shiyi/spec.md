## 1. 已确认的决策

| 项目 | 决策 |
|---|---|
| 目标 | 降低长期修改成本；电脑和手机访问同一份学习进度 |
| 使用规模 | 少于 3 人；所有人共用进度、设置、草稿和历史 |
| 前端 | React + TypeScript + Vite，复用现有 CSS |
| 后端 | FastAPI + Uvicorn；保留 Python 复习业务逻辑 |
| 数据 | SQLite；单实例、单 worker、一个数据目录 |
| 部署 | 用户电脑保持开机，Tailscale Serve 提供私有 HTTPS 入口 |
| 代码管理 | 默认沿用现有仓库及 origin；提交范围单独列明 |
| 协作 | 主 agent 统筹，前后端边界冻结后按目录并行，独立复核 |

所有用户有相同应用权限，包括修改共享草稿、导入、撤销和恢复。Tailscale 控制谁能访问，不增加应用注册、个人账号、角色系统或 `user_id` 数据迁移。访问名单是本机部署配置，不写入公开仓库。

本次选型不承诺固定的 token 节省比例。通过保留有效代码、减少同时改动的层次、限定 agent 上下文和避免反复全量测试控制成本。

### 4.2 构建与资源路径

- `build_content.py` 增加明确的输出目录；旧输出默认保持可运行，React 构建选择 JSON 模式。两种格式共用同一组内容处理函数，不维护两份题库逻辑。
- React 构建流程：先生成 `frontend/public/content/library.json` 与 `notes/`，再运行 Vite，将它们复制到 `frontend/dist/content/`。
- `library.json` 的顶层仍是 `{version, topics}`，保留稳定 UID、源码 hash、完整代码与题解信息。生成结果可重建，不作为人工编辑源。
- 题解 URL 统一为 `/content/notes/lc-N.html`；题解中的返回链接应指向真实应用入口，不能沿用会落到 `/content/index.html` 的 `../index.html`。
- FastAPI 对 `/api/*` 先匹配。缺失的 API/JSON/JS/题解返回真实 404，不能用 SPA 的 HTML 回退掩盖。
- React 迁移期入口为同 origin 的 `/app/`，Vite 资源 base 和静态挂载一致；最终入口恢复为 `/`。最终以 hash 路由保存页面/题目/筛选，不增加路由依赖，不把草稿写进 URL。
- 必须调整硬编码旧题库路径的测试。旧格式测试在兼容阶段保留，最终基于 JSON 构建产物检查，不能只删断言。
- Vite 不得以旧 `dist/` 为输出目录。其默认构建可能清空输出目录，见 [Vite 构建规则](https://vite.dev/config/build-options.html#build-emptyoutdir)。

### 4.3 开发与日常运行

实施阶段先核对本机运行时、Vite 的 Node 要求和 CI 支持，再固定 Python/Node 版本和依赖锁；本 spec 不猜测版本号。Python 依赖按所选版本一次生成锁文件，后续安装使用同一锁文件；前端使用 `npm ci`。

完成一次安装和构建后，日常双击只启动 Python/Uvicorn，不要求运行 Vite 或 Node 服务。缺少环境/构建产物时给明确准备提示，不在每次启动时联网安装或重新打包。保留 `--no-open`、`--port`、`--data-dir`。

开发默认使用单独端口和临时数据目录。主 agent 集成时可采用构建后由 Python 同源提供页面的方式。若启用 Vite 热更新代理，只开放明确的开发 Host/Origin，且只连接临时数据，不能放宽生产来源规则。参考 [Vite 后端集成](https://vite.dev/guide/backend-integration.html)。

## 5. API 与状态契约

接口迁移先保持 `apiVersion: 2`，不改变 SQLite `SCHEMA=1`。由主 agent 冻结下列合同，前后端不得各自改名。

| 接口 | 保留行为 |
|---|---|
| `GET /api/session` | 返回应用标识、apiVersion、当前服务 token、dataDirectory；允许增加明确兼容的字段 |
| `GET /api/state` | 返回 state/drafts/settings/revision/databaseId |
| `GET /api/status` | 返回当前数据库、备份状态及现有快照字段 |
| `GET /api/learning` | 保留总览、按日统计、记录、今日完成和最近提交结构 |
| `GET /api/history?before=&uid=` | 保留分页、题目筛选、撤销条件 |
| `GET /api/export` | 保留原 JSON 导出格式和合并语义 |
| `POST /api/command` | `{id,type,payload,databaseId}`；支持 review/undo/note/draft/settings/import/migrate/restore |
| `POST /api/backup` | 手动创建一致性 SQLite 备份 |

响应错误保留 `{error, detail}` 和现有 400/401/403/404/409/413/415/503 分类。FastAPI/Pydantic 默认 422、类型自动转换不能无意改变旧行为；评分的布尔值不能被当作整数接受。保留 JSON Content-Type 和 16 MB 请求体边界，流式计数/缺失或伪造长度也要受限，不能只信 Content-Length。

UI 临时状态、已确认数据库快照、待提交操作分清职责。保存状态由统一保存模块发出；React 渲染/effect 不生成评分命令。轮询、订阅、事件监听成对清理；开发 StrictMode 不重复启动队列或提交。

继续使用固定请求 ID、指纹、`expectedAt` 和 `databaseId`。保留已经发出的请求体，不因重试产生新 ID；新旧前端切换不能改写待提交操作的业务内容。

## 6. 数据与运行安全边界

- 默认数据库仍是当前应用目录的 `data/review.sqlite3`，不得因目录整理创建一份空库冒充旧进度。
- 使用一个 Uvicorn worker。`DataLease` 在服务整个生命周期持有；`Database` 和现有 `RLock` 为单实例共享。SQLite 保留 WAL、事务和备份机制。
- 同步 `sqlite3` 操作使用同步路由/受控线程池；不在 async 路由直接阻塞事件循环，也不把 RLock 当作跨进程锁。
- 生命周期创建数据库与 token，正常退出顺序处理备份和 lease 释放；启动失败释放资源。参考 [FastAPI lifespan](https://fastapi.tiangolo.com/advanced/events/)。
- JSON 导出用于携带数据与合并，不能作为精确回滚副本：它没有完整的撤销前后快照、幂等回执与所有元数据。精确迁移/回滚使用 SQLite 在线备份，或停服后复制整个 data 目录。
- 实施前恢复点另存到不会被“保留30份”轮转清理的本机目录；成功核对恢复前不删除。备份文件始终留在Git之外。
- 真数据仅在本地正式切换/恢复阶段接触；自动化测试和 agent 使用临时数据及人工构造夹具，不复制私人草稿到测试、截图或 CI。
- 保留本地恢复工具对损坏文件的归档、完整性检查和原子替换。应用代码回退与数据库恢复是两件事，不用 `git checkout` 代替恢复数据库。

## 7. Tailscale、共享时间与入口迁移

### 7.1 私有访问

Uvicorn 保持监听 `127.0.0.1:8765`，Tailscale Serve 代理到该端口。使用 Serve 的私有 HTTPS 入口，不启用 Funnel、公网端口转发或通配 CORS。访问授权限制为实际参与者/设备；同一数据库允许同时通过本机与私有入口访问。参考 [Tailscale Serve](https://tailscale.com/docs/features/tailscale-serve)。

生产 Host/Origin 配置只包含实际本机地址与部署生成的 HTTPS 名称；外来 Host/Origin 仍拒绝。不能信任任意浏览器提供的代理/身份头。当前 token 是本机请求保护机制，远程访问资格由 Tailscale 控制；前端不能用“重新拿到 token”替代访问授权。

所有参与者都操作同一份数据，界面需清楚说明“共享进度”，草稿冲突和恢复确认保持可见。本版无个人私有笔记空间。

### 7.2 日期口径

共享额度和“今天”只采用一个服务端学习时区。首次部署建议 `America/Chicago`（当前环境），正式启用时核对主机时区；把选择作为本机启动配置，不写个人配置进仓库。新增可配置的时区参数，并在 session 返回 `timeZone` 和服务端当前时间供客户端统一计算；这是 API v2 的加法扩展。

时间点继续保存 Unix 毫秒；每日额度、日期筛选、七日统计、前端队列和展示口径统一使用该时区。学习日边界与统计分桶跨午夜/夏令时时使用日历日运算，不能按固定24小时分桶。复习到期算法保持原实现语义：10分钟重试使用经过时间，1/3/7/14/30天继续按服务端本地日历推进；此次只统一时区，不重设间隔策略。老数据不重写时间戳。浏览器时区不同的两个客户端仍显示同一共享学习日。

当前运行平台是macOS/Linux，可在初始化数据库前校验IANA时区并一次设置进程 `TZ`/`time.tzset()`，使既有Python本地日期与SQLite `localtime` 保持一致；不得逐请求改进程时区。配置无效时应拒绝启动并提示，不悄悄退回另一个时区。

### 7.3 浏览器来源变化

路径从 `/` 到 `/app/` 不改变 origin；从 `127.0.0.1` 到 `localhost`、新端口或 Tailscale HTTPS 域名都会改变 origin，原 localStorage 不会自动搬过去。

迁移步骤：

1. 在原浏览器入口处理/导出待保存请求和旧版进度，记录是否仍有待处理冲突。
2. 原入口正常情况下先清空已完成的发送队列，再切换 React；保留旧 localStorage 来源以便恢复。
3. 无法发送的操作按现有导出机制保存，从新入口导入；保留请求 ID、原始业务内容和原 `databaseId`，服务端去重。
4. 新入口连接同一数据库，核对进度、草稿与历史；同源新旧页面不同时作为两个迁移写入客户端运行。
5. 若两设备确实产生冲突，由界面处理；不得以“最近打开的页面”为准覆盖。

旧格式的 localStorage 导入在新前端继续兼容。直接清理浏览器数据不是迁移步骤。

已确认一个需要随迁移修正的旧缺口：`dist/app.js` 的待保存文件导入调用 `enqueue(type,payload,id)`，会丢弃文件中的原 `databaseId` 并绑定当前数据库。这可能绕过恢复后的epoch提醒。新前端导入必须保留原epoch；发现不同epoch或缺少epoch时先展示迁移确认，不得自动改绑重放。用户明确决定将某项旧操作应用到当前库时，使用显式冲突解决路径并保留原导出文件。此项是有意修正的数据保护行为，需要回归检查。

另一个界面语义需明确：存在待提交操作时，旧“导出完整备份”实际导出的是队列文件。新界面应准确说明本次导出的是待保存内容还是完整已提交记录；仍不能将其中任意JSON文件描述为精确数据库恢复点。
