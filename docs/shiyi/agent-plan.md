# 拾忆重构：sub-agent 启动与执行计划

状态：实施前计划。架构和验收以 [spec](spec.md) 为准；Git 操作见 [GitHub 计划](github-plan.md)。

## 1. 本轮与实施轮的区别

本轮已使用两个只读 sub-agent 检查前后端迁移风险，以及一个只读 sub-agent 复核三份文档的一致性；它们不修改代码、不读取真实数据库、不提交。本文规定后续正式实施的启动顺序，不表示实现已经开始。

主 agent 始终负责结果、契约、共享文件、用户沟通与 GitHub 操作。sub-agent 是当前任务的工作分工，不另建用户侧 Codex 任务。

## 2. 总体安排

```text
主 agent：M0 基线 → M1 契约、构建目录及任务所有权
                        ├─ backend agent：HTTP迁移、兼容性检查
                        └─ frontend agent：学习中心 → 其余React页面
主 agent：题库构建、脚本、CI → M3集成（先关闭编辑窗口）
review agent：只读核对验收矩阵、发现问题 → 对应owner修正
主 agent：M4 Tailscale和真机验收 → M5精确提交、PR、交付
```

默认同时只有主 agent 和两个实施 agent。review agent 在待审版本稳定后启动；不要让四个 agent 同时改代码。某阶段没有有用的独立任务时，由主 agent 顺序完成，避免为并行而拆分。

## 3. 启动前置条件

1. 原工作区有 52 个已跟踪文件的未提交改动，应用目录尚未跟踪；直接从 HEAD 创建工作区不会自动带上应用。这一点先由主 agent 按 GitHub 计划处理。
2. 主 agent 建立隔离实施工作区、复制审核后的基线、完成基线提交与测试，记录完整 commit SHA。
3. 冻结 API v2、错误结构、时区扩展、临时 `/app/` 与最终 `/`、内容 URL、默认 data 路径和旧队列格式。
4. 主 agent 建好共享构建骨架与依赖清单，记录前后端允许修改目录；sub-agent 不自行引入未约定依赖。
5. 向每个 agent 提供绝对实施工作区路径。共享工具的默认 cwd 可能仍指向原工作区，因此每次文件操作必须显式指定路径/workdir，不能依赖默认 cwd。

基线未完成时，允许只读研究，不启动并行改码。

## 4. 文件所有权

表中的路径相对于实施工作区中的应用根目录 `04-Outputs/数组与矩阵记忆卡/`。

| Owner | 可独占修改 | 不得自行修改 |
|---|---|---|
| 主 agent | 根启动器/README/.gitignore、依赖清单及锁文件、`build_content.py`、题库检查、Vite/TS配置、CI、spec、Git | 其他 agent 活跃编辑的文件 |
| backend agent | `backend/`、`database.py`、`data_lock.py`、`recover.py`、`tests/api_test.py`、`tests/database_test.py`、`tests/learning_test.py` | 前端、构建脚本、根启动器、任何真实 data、Git操作 |
| frontend agent | `frontend/src/`、React入口模板、前端测试；经指派后迁移旧保存/model测试 | 后端、依赖/锁文件、Vite共享配置、题库源、任何真实 data、Git操作 |
| review agent | 只读所有实施文件及指定日志 | 不修文件、不更新依赖、不启动真库、不提交 |

`start.py` 的调用约定由主 agent 与 backend agent 先确定；backend agent 返回 factory 的名字/参数，主 agent 接入。frontend agent 若需要新依赖，说明它要替代的现有代码和理由，由主 agent 单次更新清单与锁文件。

所有权转交必须在原 owner 停止编辑后通过一条消息确认。不要把两个任务的目录边界设置为有重叠的通配范围。

## 6. 分阶段交接

| 时点 | agent 交付 | 主 agent 行动 |
|---|---|---|
| 后端首个里程碑 | 兼容旧前端的API和临时库检查 | 接入启动器，核对状态码与数据目录；后续补齐来源/时区配置代码 |
| 前端首个里程碑 | 学习中心在冻结API上可用 | 核对筛选、分页、手机布局、题解路径 |
| 全量页面迁移 | 页面清单及保存队列兼容结果 | 联调实际API，不以mock结果代替 |
| 集成完成 | 含来源/时区代码在内的所有owner停止编辑，交付限制清单 | 建待审提交/稳定差异，启动只读review |
| 修复完成 | 只重跑问题相关检查 | 统一跑最终必要回归，避免多agent重复全套 |
| 发布准备 | 无未解决的数据保护问题 | 真机访问、来源迁移、干净checkout检查、PR |

后端契约变化时，先暂停依赖该契约的前端工作；两边确认新合同后再继续。若同步变更会扩大范围，主 agent 回到最小兼容实现。

M3的切换只发生在实施目录和临时数据上，原实际使用入口保留到M4处理完队列。M4原则上只配置和验收；若因此产生新的代码修正，重新走owner修复与相关差异review，不能直接跳到发布。

## 7. Git、测试与成本纪律

- 默认各 agent 在同一个隔离实施工作区按目录分工；只有主 agent 执行 stage/commit/merge/push。禁止并行 Git 写操作。
- 如果后续工作确实需要重叠文件，可从已提交基线创建各自 worktree，先停共享编辑，再用独立分支/提交交接；不要同时使用两套协作模式。
- 只读review启动时编辑者已停止；避免报告刚被改掉的行号。
- 每个任务只读其范围和必要契约。反馈最多围绕“完成、证据、阻塞、交接”，不要复述整个spec。
- 有新修改、失败或未解决风险才扩大测试；同一套成功的全量检查由主 agent 统一记录即可。
- 冲突、测试失败和未完成真机验收不能以节省token为由跳过；token成本没有本次实测预算或节省比例。
- 发布、账号配置和真实数据操作归主 agent；任何缺少用户凭证/设备的动作明确列为待完成，不把权限假设交给sub-agent自行处理。
